# DRIVER-VERIFY-SPEC

[English](DRIVER-VERIFY-SPEC.md) | 中文

> 版本 1.3.2 · 条款 DVER-001 至 DVER-051

## 怎么读

本规范说明驱动工具怎样证明自己能用。每条规则是一个条款，带固定编号，如 `DVER-010`。条款以两行结束：「为什么」说明理由；「检查」说明怎么检查，🤖 表示由测试或脚本自动检查，👀 表示由人在评审时检查。

用词的含义：

- 必须、禁止：硬性要求。违反了，工具就不合规。
- 应该、不应该：默认的做法。只有说得出理由时才能偏离。
- 可以：允许，但不要求。

机器契约 `contract/driver-contract.json` 以数据形式记录测试编号、行为矩阵的各行、每项测试和每一行的适用条件、成熟度等级和证据种类。`contract/schemas/` 里的 Schema 规定存放证据的各种文件。它们是工具所固定的规范版本里的 Schema：工具项目不复制它们，`check_project` 从那个版本里读取。重复契约值的表格带有契约标记。这类表格与契约不一致时，以契约为准。

## 适用范围

本规范适用于每个驱动工具，也适用于驱动运行时。内容包括：

- 每个工具都要跑的两组一致性测试：通用一致性测试（G 组和 R 组）和驱动一致性测试（D 组）
- 模拟宿主：在测试里代替被驱动的软件
- 每个领域命令、每个调用适配能力的标准命令各自的行为矩阵
- 每条命令都要声明的成熟度和证据
- 在真实软件上的验收

本规范不重复被测试的规则，每项测试都写明它检查哪些条款。

有两种运行用来测试工具，各自证明的东西不同。一致性测试在模拟宿主上运行，证明运行时在各种情况下都能为这个工具正确处理。真实运行会用到工具真正的适配层和真实软件。只有真实运行和在真实软件上的 Agent 评测才算命令成熟度的证据（DVER-021、DVER-040）。

贯穿本规范的一句话：能测才算数。没运行不等于通过，模拟不等于真实，没核实不等于成功。

## 术语

| 术语 | 含义 |
|---|---|
| 驱动运行时 | 每个工具原样复制的共用代码，实现内置命令、标准命令、写操作流程和回执 |
| 领域命令 | 工具作者自己登记的命令，区别于运行时提供的内置命令和标准命令 |
| 写命令 | 声明的效果不是 `observe` 的命令（DCLI-051） |
| 中止命令 | 只让进行中的工作停下来的命令：`stop` 命令或 `job cancel`，登记时带 `halt: true`。它立即执行，不需要确认（DSEC-018） |
| 一致性测试 | 本规范两组测试中的一项：通用（G00 至 G10、R01 至 R05）和驱动（D01 至 D26） |
| 写命令样例 | 对某个写命令的一次有效调用的参数，放在它行为矩阵的 `normal` 行里，供通用一致性测试使用（DVER-002） |
| 模拟宿主 | tool-driver-cli-spec 仓库提供的小程序，在测试中代替被驱动的软件（DVER-020） |
| 行为矩阵 | 每条命令一个 JSON 文件，每种情况一行：参数、期望结果、实际结果和证据（DVER-030） |
| 成熟度 | 一条命令被证明到什么程度：`draft`、`verified` 或 `stable`（DVER-040） |
| 证据 | 证明成熟度属实的文件，由证据引用指向它（DVER-041） |
| 模拟结果 | 用模拟宿主或模拟设备得到的结果，从不算作证据（DVER-021） |
| 真实运行 | 在授权目标上，用工具真正的适配层驱动真实软件 |
| 真实软件记录 | 一次真实运行留下的 JSON 记录，放在 `docs/evidence/`（DVER-042） |
| 评测报告 | 记录 Agent 做工具评测题结果的 JSON 文件 `docs/evidence/eval-*.json`（DSKL-043） |
| 真实软件验收 | 在真实软件上检查工具，做法写在 `docs/E2E.md` |
| 授权目标 | 人允许真实运行使用的文件、文件夹或设备，列在 `docs/E2E.md` 里（DVER-050） |

## 运行时与工具的分工

| 方面 | 运行时和 tool-driver-cli-spec 仓库提供 | 工具作者要做 |
|---|---|---|
| 一致性测试 | 两组测试，可以从命令行运行任何工具 | 每次合并和发布时，在每个出包的平台上用 CI 跑这两组测试 |
| 写命令样例 | 使用样例的 G 组测试；内置命令和标准命令的样例 | 每个领域写命令行为矩阵里的 `normal` 行 |
| 模拟宿主 | 模拟宿主，通过 `<PREFIX>_FAKE_HOST`（DVER-023）和宿主协议接入 | 不用写 |
| 行为矩阵 | 各行及其适用条件、矩阵的 Schema 和矩阵运行器 | 每个领域命令、每个调用适配能力的标准命令各一个矩阵文件 |
| 成熟度与证据 | `reference` 展示成熟度和证据；`check_project` 核对等级与证据 | 为每条命令声明等级和证据，并让证据保持有效 |
| 真实软件验收 | 真实软件记录和评测报告的 Schema | 在授权目标上运行；编写 `docs/E2E.md` 和 `docs/evidence/` 下的记录 |

## 通用一致性测试

### DVER-001 一致性测试套件

驱动运行时附带两组一致性测试：通用一致性测试（DVER-003）和驱动一致性测试（DVER-010）。每个工具必须在每次合并和每次发布时，在它出包的每个平台上跑这两组测试（DREPO-041）。工具禁止跳过、削弱或修改任何一项测试，也禁止把某项测试标为预期失败。适用（DVER-010）却没有运行的测试按失败计。这两组测试禁止依赖真实软件、许可或设备，由模拟宿主代替它们（DVER-020）。

为什么：这些测试检查的是每个 Agent 都依赖的规则。跳过一项，坏掉的规则就藏在一次「全部通过」的构建后面。
检查：👀 评审 CI 工作流：两组测试在每个出包的平台上运行，没有跳过或改动任何一项。

### DVER-002 写命令样例

工具必须为每个领域写命令提供一个有效样例，写成它行为矩阵（DVER-030）里 `normal` 行的参数。样例是一次调用的参数：命令接受这些参数，带 `--dry-run` 运行时返回有效的预览（G02）。通用一致性测试在各项写操作测试里，在模拟宿主上（DVER-020）运行这些样例。内置命令和标准命令的样例由测试套件自带。成熟度为 `draft` 的命令同样需要样例（DVER-040）。

同一组参数既要在模拟宿主上用，也要在真实软件上用。所以样例必须只通过下表的占位符指明会话、文档、设备、输出目录、作业和输入文件：一致性测试用模拟宿主的值填入，矩阵运行器用授权目标（DVER-050）的值填入。行为矩阵的每一行都可以使用这些占位符。

<!-- contract:sample_placeholders -->
| 占位符 | 在模拟宿主上 | 在真实软件上 |
|---|---|---|
| `{session}` | 模拟宿主的一个实例 | 为这次运行启动的实例 |
| `{doc}` | 模拟宿主的一个文档：在该实例中打开的文档，文件模式下则是一个文件 | 授权的文档或文件 |
| `{device}` | 模拟宿主的设备 | 授权的设备 |
| `{dir}` | 一个新建的空临时目录，用来放输出文件 | 授权文件夹里新建的一个空目录 |
| `{job}` | 测试套件用长命令的样例启动的一个作业 | 同一次运行中启动的作业：`--set job=<id>`，或者先运行某个长命令的 `normal` 行、由它启动的作业（`run_matrix --job-from`） |
| `{inputs}` | 项目的 `tests/inputs/` 文件夹：命令只读取的文件，比如设计描述 | 同一个文件夹 |

为什么：测试套件猜不出领域命令的有效参数。没有样例，确认相关的测试就没法在这个命令上运行；样例放在矩阵里，要更新时只有一处。
检查：🤖 通用一致性测试 G00。

## 驱动一致性测试

### DVER-010 驱动一致性测试

驱动一致性测试必须包含下表的各项，每个工具必须通过所有适用于它的测试。每项测试什么时候适用，契约在 `conformance.driver[].applies_when` 里列出，取值来自 `conformance.applies_when_values`；满足其中任意一个条件，测试就适用：

- `always`：每个工具都适用；
- `writes`：工具有写命令；
- `direct_writes`：工具有写命令至少在一种模式下属于直接执行级（DCLI-052）；
- `documents`：工具在文件模式或会话模式下操作文档；
- `dangerous`：工具有在危险级运行的命令，哪怕只在某些情况下（DCLI-051）；
- `jobs`：工具有登记了 `jobs: true` 的命令，它的长任务由软件运行；
- `session` 或 `device`：工具支持该模式；
- `host_component`：工具有宿主组件；
- `physical`：工具有带 `physical` 效果的命令；
- `halt`：工具在会话模式或设备模式下有中止命令（DSEC-018）；
- `long_jobs`：工具有登记了 `long: true`、由运行时运行长任务的命令（DCLI-065）。

哪些测试适用，由运行时根据命令登记（DCLI-029）判断，不由工具作者决定。不适用的测试报告为不适用，并写明条件。测试运行 CLI 时由模拟宿主代替被驱动的软件，所以结果属于模拟结果（DVER-021）。最后一列是每项测试检查的条款。

### DVER-011 黑盒测试

测试必须把 CLI 当作黑盒：从命令行把它作为单独的进程启动，只根据退出码、stdout 上的信封和模拟宿主收到的内容判断结果。测试禁止导入工具的代码，也禁止直接调用运行时的函数。每次运行必须使用临时的状态目录（DSEC-034）。这样测试就与实现语言无关：用其他语言写的运行时必须原样通过同一套测试。

为什么：Agent 只看得到命令行。从内部检查的测试会放过让 Agent 失败的工具，还会把测试绑死在一种语言上。
检查：👀 评审测试代码：每项测试都以进程方式启动 CLI。

## 模拟宿主

### DVER-020 模拟宿主

tool-driver-cli-spec 仓库提供模拟宿主：一个在测试中代替被驱动软件的小程序。它必须能代替工具接入软件的两种方式：CLI 进程内的适配层（DCLI-260），经模拟宿主自己的地址接入（DVER-023）；以及宿主组件，经宿主协议接入（DCLI-270 至 DCLI-280）。两种方式的载荷都按 `contract/schemas/adapter.schema.json`。它也是宿主协议的参考实现（DCLI-281）。它必须能模拟：

- 同时运行的多个实例
- 内存中的文档，以及未保存的修改
- 弹窗、主线程忙、实例没有及时回复，以及回复之前连接就关闭
- 人在软件里手动修改文档
- 长任务
- 一台模拟设备，可以处于每一种设备状态（DCLI-230）

标准适配能力由模拟宿主自己实现。对领域命令，它根据命令的登记（DCLI-029）和这次调用的输入，代替工具的适配层作答。目标是调用通过 `--id`、`--ids` 或每个 `--input` 条目的 `id`（DCLI-064）选中的对象，位于调用指明的会话、文档或设备中；调用没有选中对象时，目标就是它指明的文档，没有文档时是它指明的设备；两者都没有指明的调用没有目标。命令自己登记的其余参数都是被修改的字段。除非测试另行设定，模拟宿主把任何对象 ID 都当作存在。它为每个目标预览一项修改，把修改写进内存，读回时返回预览中的值。对 `artifact` 命令，它的 `output` 参数指明的文件起初不存在，执行时由模拟宿主写出（DCLI-029）；没有 `output` 参数的 `artifact` 命令，由模拟宿主自己起名写出一个文件，就像自己给文件起名的软件那样。文档的种类取新建它或打开它所在实例时给的种类（`--kind`），没有时取评测题为它的文件后缀设定的种类，再没有时取测试设定的种类，所以登记了 `doc_kinds` 的命令总是在它适用的文档上运行（DCLI-210）。不是模拟宿主格式的文件，当作空文档打开。工具作者不用为它写任何东西。测试必须能让模拟宿主进入上面每一种情况；能让任何一次适配调用失败、挂住或读回不同的值，既可以针对整个调用，也可以只针对批量中的某一项；还能读取模拟宿主的状态，从而看出修改有没有到达、到达了几次，以及哪些请求违反了协议或载荷的规定。

一致性测试运行工具真实的 CLI 和真实的命令登记，由模拟宿主代替被驱动的软件。它们证明运行时在每种情况下都能为这个工具正确处理，但从不运行工具自己的适配层（DVER-021）。

为什么：最要紧的失败，比如弹窗和断连，在真实软件里很少见，也很难按需制造。
检查：🤖 驱动一致性测试 D01 至 D26，它们需要上面每一种情况。

### DVER-021 模拟结果不算证据

每种运行证明的东西不同：

| 运行 | 运行的是什么 | 证明什么 |
|---|---|---|
| 一致性测试（DVER-001） | 工具的 CLI 和命令登记，由模拟宿主代替被驱动的软件和工具的适配层 | 运行时在每种情况下都能为这个工具正确处理 |
| 真实运行（DVER-042） | 工具真正的适配层，配合真实软件 | 命令能与软件配合工作；`verified` 需要它 |

用模拟宿主或模拟设备（DSEC-062）得到的结果都是模拟结果。禁止把它们当作真实软件上的结果展示，也禁止用它们支撑成熟度等级（DVER-040）或 ✅ verified 标签（DREPO-022、DREPO-023）。

为什么：模拟宿主的行为是作者写出来的，不是软件真实的行为。把它算作证据，就是声称了从没验证过的支持。
检查：🤖 `check_project`：没有当前有效的 `live:` 记录的命令和支持矩阵行，一律不得标为 `verified`。

### DVER-022 规范仓库 CI 中的模拟宿主

tool-driver-cli-spec 仓库必须在每次合并和每次发布时，在 Windows、macOS 和 Linux 的 CI 上用模拟宿主运行驱动运行时、项目模板和两组一致性测试。它还必须在那里用脚本代理运行 DSKL-041 的评测套件。工具自己的评测只覆盖结果取决于工具作者所写文字的场景（DSKL-042）。运行时单元测试也必须在同一个 CI 里、在这三个系统上运行。它和两组一致性测试一样是必过的检查：不通过就不能合并，也不能发布。它覆盖内置命令，以及「检查」行引用运行时单元测试的每条规则。

为什么：每个工具都原样复制运行时。在这里发现的问题修一次就够了，不用每个工具各修一遍。
检查：👀 评审 tool-driver-cli-spec 仓库的 CI 工作流。

### DVER-023 让工具连到模拟宿主

环境变量 `<PREFIX>_FAKE_HOST` 写有模拟宿主的地址时，运行时必须用模拟宿主代替工具的适配层和被驱动的软件：

- 必须把每一次适配能力调用（DCLI-260），不论 CLI 侧还是实例侧，都以同名请求发到这个地址，分帧和握手按宿主协议（DCLI-272、DCLI-273），载荷按 `contract/schemas/adapter.schema.json`。
- 工具有宿主组件（DCLI-240）时，必须把实例侧的调用发给模拟宿主在状态目录 `hosts/` 下登记的实例（DCLI-271），这样测试也能检验运行时自己的宿主协议客户端。
- 每份回执都必须带 `simulated: true`，`context` 和 `doctor` 必须把模拟宿主写成被驱动的软件（DVER-021）。

运行时禁止从这个环境变量以外的任何文件、参数或设置读取这个地址。

为什么：黑盒测试需要一个对任何语言的运行时都适用的开关。每份回执都打上标记，误留的环境变量就没法把模拟结果冒充成真实结果。
检查：🤖 每一项一致性测试（DVER-001）都通过这个环境变量连接工具；通用一致性测试 R04 和运行时单元测试检查标记。

## 行为矩阵

### DVER-030 行为矩阵

每个领域命令，以及每个所调用的适配能力都由工具实现了的标准命令（DCLI-200、DCLI-260），都必须有一张行为矩阵：`tests/matrix/` 里每条命令一个 JSON 文件，以命令路径命名，并通过 `contract/schemas/behavior-matrix.schema.json` 的校验。内置命令、不调用适配能力的标准命令（如 `knowledge` 各命令），以及所需能力工具没有实现、因而返回 `E_UNSUPPORTED` 的标准命令，都不需要矩阵，由运行时单元测试覆盖（DVER-022）。

文件把下表的每一行各列一次，每行是一种情况。适用于这条命令的行写明参数和期望结果：退出码，失败时再加错误码。这一行运行过之后，还要写上实际结果和证据引用（DVER-041）。不适用的行写 `applies: false` 和原因。每行什么时候适用，契约在 `behavior_matrix_rows[].applies_when` 里列出；这些取值针对这条命令来判断：`writes` 指它是写命令，`session` 和 `device` 指它支持该模式，`documents` 指它操作文档，`host_component` 指它经宿主组件接入软件，`always` 总是成立。只有条件成立的行才会运行。

<!-- contract:behavior_matrix_rows -->
| 行 | 组 | 适用条件 | 情况 |
|---|---|---|---|
| `normal` 正常 | 通用 | `always` | 一次成功的有效调用；写命令的这一行参数就是它的样例（DVER-002） |
| `empty` 空结果 | 通用 | `always` | 一次有效调用，但没有可返回的内容 |
| `invalid_input` 无效输入 | 通用 | `always` | 参数格式错误或超出范围，或者物理量没带单位 |
| `not_found` 找不到 | 通用 | `always` | 指定的对象、文档、会话或长任务不存在 |
| `ambiguous` 名字有歧义 | 通用 | `always` | 一个名字匹配到多个对象或实例 |
| `conflict` 冲突 | 通用 | `writes` | 前置条件不满足，比如目标被锁或文档已变 |
| `no_scope` 没有授权 | 通用 | `writes` | 没有授权范围文件，或授权范围没有覆盖这次调用 |
| `busy` 软件忙 | 驱动 | `session`, `device` | 软件主线程或设备忙，或者实例没有及时回复 |
| `dialog` 弹窗 | 驱动 | `session` | 弹窗挡住了软件 |
| `disconnect` 断连 | 驱动 | `session`, `device`, `host_component` | 调用过程中连接断开 |
| `unsaved` 未保存 | 驱动 | `documents` | 文档有未保存的修改 |
| `read_back_mismatch` 读回不符 | 驱动 | `writes` | 读回的值与期望值的差超出登记的容差 |

条件不成立的行，必须标为不适用。条件成立、但对这条命令不可能发生的行，也必须留在文件里，标为不适用并写明原因。

`read_back_mismatch` 行检查读回读的是软件，而不是工具自己的预期。正确的预览能预料到软件会存下什么，所以这一行要从外部制造：`run_matrix --row read_back_mismatch` 让工具在读回之前等一会儿（环境变量 `<PREFIX>_TEST_PAUSE_BEFORE_READ_BACK`，最长 `matrix.max_pause_seconds`；等待期间工具在状态目录里写出 `pause.json`），在这段时间里，由人或 `--tamper` 给出的命令改掉软件里刚写入的内容，或者删除写操作生成的文件。`--tamper` 命令里的 `{python}` 代表 `run_matrix` 自己所用的解释器；这条命令运行时不带那个变量，所以可以调用工具。只有真的不一致时等待才提前结束：软件忙或被挡住时，工具继续等。`run_matrix` 和对待每一行一样，用令牌确认两步确认级和危险级的写操作，所以等待落在真正派发的那次调用上。长命令的等待发生在后台进程里，这一行按长任务的结束情况判定；登记了 `verify_after_save` 的命令，等待发生在写操作之后的那次 `doc save`。工具报告 `E_VERIFY_FAILED` 时，这一行通过；真实软件记录把这次运行标为 `tampered`。凡是结果能在这段时间里从外部改掉的写操作，这一行都适用，生成文件的写操作也一样。只有做不到时才不适用，比如交给外部系统的内容或物理动作，原因必须写明。

登记了 `doc_kinds` 的命令（DCLI-029），必须在它列出的每一种文档上通过 `normal` 行；`run_matrix --kind <kind>` 记下每次运行用的文档种类，并把 `normal` 行在每种文档上的证据分别记在 `kind_evidence` 里，每种文档上以最新一次运行为准。参数指向的对象在不同种类的文档里不一样时，`normal` 行可以给出 `kind_arguments`，按种类写各自的参数；其余种类用 `arguments`。其余各行用一种文档即可。登记了 `verify_after_save` 的命令，`normal` 行在写操作之后对同一份文档运行 `doc save`，只有这次保存核实了修改，这一行才通过（DCLI-057）。

各行在授权目标上用真实软件运行（DVER-031、DVER-050）。矩阵运行器 `run_matrix` 随本规范提供：它填入占位符（DVER-002），运行适用的行，写一份真实软件记录并在其中写明每一行（DVER-042），再给每一行填上实际结果和 `live:` 证据。它自己为每次运行写授权范围文件，授予 Authorized Targets 里的目标上的全部效果，包括 `dangerous`；`--set session=` 指明实例时，也授予它的新文档 `untitled:<session-id>/`；`no_scope` 行在没有授权范围文件的情况下运行，环境变量指定的授权范围文件不用。运行失败却没有契约里的错误码时（比如工具崩溃），这次运行不给出实际结果：真实软件记录把它记为失败，这一行的实际结果和证据都被清掉，算作没运行过。写操作要求确认的行，用令牌确认，除非这一行期望的就是 `E_CONFIRMATION_REQUIRED`；长命令的行等长任务结束，取长任务的结果。适用却没有实际结果和证据的行就是没运行过。实际结果与期望结果不同，或者真实运行的 `result` 为 `fail` 的行，就是失败了。没运行过或失败了的行，禁止算作通过。

适用、但在真实软件上无法按需制造的行，如 `disconnect`，可以标为 `unrunnable` 并写明原因。这样的行不需要真实运行，运行时怎样处理这种情况由驱动一致性测试覆盖（DVER-010）。`normal`、`dialog` 和 `read_back_mismatch` 三行禁止标为 `unrunnable`（DVER-031）。

为什么：Agent 每天都会遇到这些情况。不知道命令在这些情况下怎么表现，它就会在最糟的时候出错。矩阵是列全了每一行的数据文件，脚本一眼就能看出缺了哪一行、哪一行从没运行过。
检查：🤖 `check_project` 校验每个矩阵文件，把每行的 `applies` 与契约的条件核对，并把每行的实际结果与期望结果核对；👀 评审「不可能发生」和「无法按需制造」的那些行写的原因。

### DVER-031 适配层在真实软件上的行为

模拟宿主无法说明真正的适配层面对真实软件时的表现：能不能识别软件真正的弹窗，读回的是不是软件里真实的值。只有真实运行才会用到真正的适配层。这些必须在授权目标上（DVER-050）用真实软件运行行为矩阵来检查。关于它们的结论必须引用真实软件的证据，禁止用模拟结果支撑（DVER-021）。

为什么：模拟的弹窗长什么样由测试说了算。只有真实软件才能说明适配层能不能看到它的弹窗、读对它的值。
检查：🤖 `check_project`：每条 `verified` 命令的矩阵里，`normal` 行，以及适用时的 `dialog` 和 `read_back_mismatch` 两行，都已凭 `live:` 证据通过，且都没有标为 `unrunnable`。

## 成熟度与证据

### DVER-040 成熟度等级

每条命令都必须声明成熟度等级和支撑它的证据引用，`reference` 会展示这两项（DCLI-031）。等级禁止高于证据能支撑的程度。内置命令，以及不调用适配能力的标准命令，等级由运行时声明，以运行时单元测试为依据（DVER-022）。每一级都需要低一级的全部证据，再加上本级自己的证据：

<!-- contract:maturity_levels -->
| 等级 | 含义 | 需要的证据 |
|---|---|---|
| `draft` | 已声明，还没在真实软件上验证，接口还可能变 | 无；写命令仍要有样例（G00） |
| `verified` | 用真正的适配层在真实软件上运行过，并有记录 | 当前有效的 `live:` 证据，表明行为矩阵里每一个适用的行都已通过，标为 `unrunnable` 的行除外，并且 `normal` 行在命令列出的每一种文档上都已通过（DVER-030、DVER-043） |
| `stable` | 还通过了评测，没有未关闭的严重缺陷 | 另加当前有效的评测结果，由 `eval:` 引用指明（DSKL-043） |

只有通过的运行才算证据（DVER-030）。证据不再有效时，等级必须降到剩余证据能支撑的最高一级。严重缺陷指让命令对错误的结果报告成功、改动目标或授权范围之外的东西，或者丢失用户数据的缺陷。

为什么：成熟度告诉 Agent 和人能在多大程度上信任一条命令。等级高过证据，就是虚假的承诺。
检查：🤖 `check_project`：`reference` 中每条命令的等级都有该等级所需的证据支撑。

### DVER-041 证据引用

证据引用的格式是 `<kind>:<path>[#<anchor>]`。`path` 是相对于工具项目根目录的路径，必须指向仓库里的一个文件。`anchor` 可以省略，用来指明文件中的某一部分，比如行为矩阵的某一行。`kind` 必须取下表之一：

<!-- contract:evidence_kinds -->
| 种类 | 证明什么 | 文件在哪里 |
|---|---|---|
| `live` | 命令用真正的适配层在真实软件上运行过 | `docs/evidence/` 中的真实软件记录（DVER-042） |
| `eval` | Agent 带着工具的 Skill 在真实软件上完成了工具的评测题 | 针对 `tests/eval/` 中评测题的评测报告 `docs/evidence/eval-*.json`（DSKL-043） |

每个文件都必须通过 `contract/schemas/` 中对应 Schema 的校验：行为矩阵对应 `behavior-matrix.schema.json`，真实软件记录对应 `evidence.schema.json`，评测报告对应 `eval-report.schema.json`。

例子：`live:docs/evidence/2026-11-01-footprint-move.json#normal` 和 `eval:docs/evidence/eval-2026-11-01.json`。

为什么：指向真实文件的引用，让脚本和人都能逐条核对，而不是只能相信。
检查：🤖 `check_project`：每个引用都能解析、种类在表中、指向的文件存在，每个矩阵、记录和报告都通过对应 Schema 的校验。

### DVER-042 真实软件记录

每次真实运行都必须在 `docs/evidence/` 留下一份 JSON 记录，并通过 `contract/schemas/evidence.schema.json` 的校验。记录包含：

- `kind`：固定为 `live`
- `tool`、`tool_version` 和 `commit`：工具，以及实际运行的那个构建
- `application`：软件的名称和版本
- `os`：操作系统的完整名称；`platform`：`windows`、`macos` 或 `linux`
- `recorded_at`：运行时间，UTC
- `targets`：这次运行使用的授权目标（DVER-050）
- `runs`：每条命令一项，包括命令路径、实际运行的参数（占位符已填好，DVER-002）、退出码、`result` 和运行时所用的模式 `mode`；命令列出了文档种类时还有 `doc_kind`；`fingerprint` 是这次运行依赖的东西，`sources` 是它用到的工具代码（DVER-043）；在等待期间从外部改过结果的运行，带 `tampered: true`（DVER-030）

命令的表现符合预期时，`result` 为 `pass`，否则为 `fail`。某一项在 `matrix_row` 里写明了行为矩阵的行时，预期就是那一行的期望结果。每一项可以另加输出的信封（`envelope`）和说明。信封保持工具输出时的原样，不按当前的信封 Schema 校验，所以只要记录里的运行还算数，记录就一直有效（DVER-043）。带机密的参数必须写成 `***`（DSEC-040）。`docs/COMPATIBILITY.md` 的支持矩阵由这些记录生成（DREPO-016）。

```json
{
  "kind": "live",
  "tool": "kicad-cli",
  "tool_version": "1.4.2",
  "commit": "3f9c2ab",
  "application": {"name": "KiCad", "version": "10.0.1"},
  "os": "Windows 11 24H2 x64",
  "platform": "windows",
  "recorded_at": "2026-11-01T09:30:00Z",
  "targets": ["file:///D:/e2e/demo-board/"],
  "runs": [
    {
      "command": "footprint move",
      "arguments": ["--session", "kicad-1234", "--doc", "D:/e2e/demo-board/board.kicad_pcb", "--id", "R1", "--x", "12.5mm", "--y", "30mm"],
      "exit": 0,
      "result": "pass",
      "mode": "session",
      "matrix_row": "normal",
      "fingerprint": "4b1f0c9e2d7a6b5c8e3f1a0d9c8b7a6e5f4d3c2b1a0f9e8d7c6b5a4f3e2d1c0b"
    },
    {
      "command": "footprint move",
      "arguments": ["--session", "kicad-1234", "--doc", "D:/e2e/demo-board/board.kicad_pcb", "--id", "R1", "--x", "12.5mm", "--y", "30mm"],
      "exit": 7,
      "result": "pass",
      "mode": "session",
      "matrix_row": "busy",
      "fingerprint": "4b1f0c9e2d7a6b5c8e3f1a0d9c8b7a6e5f4d3c2b1a0f9e8d7c6b5a4f3e2d1c0b",
      "notes": "Started during a design rule check; E_BUSY with dispatch_state not_started."
    }
  ]
}
```

为什么：记录写明了版本、参数和结果，任何人都能看出跑了什么，并且能再跑一遍。事后凭记忆写的总结什么也证明不了。
检查：🤖 `check_project` 用证据 Schema 校验 `docs/evidence/` 中的每份记录。

### DVER-043 当前有效的证据

真实软件记录里的一次运行，在它依赖的东西都没有变时才算证据：它的 `fingerprint`（DVER-042）必须等于这条命令现在的指纹。指纹是两部分内容的 SHA-256。第一部分是工具登记的、`reference` 报告的这条命令，去掉不会改变命令行为的内容：`summary`、`examples`、`related_knowledge`、`output_schema`、各参数的说明、`tier_when` 里的说明，以及 `maturity` 和 `evidence`；取空默认值的字段也不算。第二部分是这次运行用到的适配层代码。从运行时被导入起，真实运行就记下它用到的工具包里的 Python 文件，以及它导入的包内其他模块；`run_matrix` 把它们存进这次运行的 `sources`。以下文件算用到：有函数开始执行过的，在运行时之前就被导入的，不经导入而被打开的（比如源码被发给软件执行的模块），以及在命令行里被点名或被复制的。被执行的文件整个算；只导入的模块不算其中函数和方法的函数体，函数名、参数和装饰器仍然算；两者都不算注释和排版。工具包里不是 Python 的文件、包里没有任何模块按名字导入的 Python 文件（比如由软件执行的脚本）、`plugin/` 里的宿主组件（它的 README 和生成的清单除外，清单只算其中列出的方法）以及 `pyproject.toml` 里的依赖，用没用到记不下来，所以总是算在内。工具包的文件指 git 已跟踪或会跟踪的文件，固定的运行时 `<pkg>/_driver/` 和命令登记 `<pkg>/commands/` 除外。没有 `sources` 的运行，比如这一行的某个进程没写下用到了什么就结束了，改为整个工具包都算。运行时不算在内，因为它对所有工具都一样，每次同步都由一致性测试检查。只是版本号变了，禁止让证据失效。评测结果按 DSKL-043 计算。没有指纹的运行或结果，只在所在记录或报告的 `tool_version` 与工具的主版本和次版本都相同时才算。不算数的证据禁止用来支撑成熟度等级（DVER-040）。

为什么：证据说明的是运行过的那份代码怎么表现。代码变了证据才过时，版本号变了不算；什么都没改的版本把所有东西重跑一遍，要花几个小时，却说明不了任何新东西。
检查：🤖 `check_project` 计算每条命令的指纹，与支撑它成熟度的那些运行比较；没有指纹的运行比较版本号。

## 真实软件验收

### DVER-050 只用授权目标

真实运行必须只使用经人授权、并列在 `docs/E2E.md` 的 Authorized Targets 一节（DREPO-017）中的文件、文件夹和设备，以及为这次运行启动的实例。命令只读取、来自项目 `tests/inputs/` 文件夹（`{inputs}`，DVER-002）的文件不算目标，不需要授权；命令写入的一切仍然必须是授权目标。这个文件夹会提交进仓库，所以只放作者自己做的或可以公开的文件，像代码一样评审。这一节是授权目标唯一的清单；其他文档，如 `AGENTS.md`，只指向它。目标是专为测试准备的文件夹或文件，或者为测试准备好的设备；覆盖整个磁盘或用户主目录的目标会被拒绝。目标只由人加入，或者在人自己发的消息里授予后由编码 Agent 加入；Agent 加入后把加的那一行告诉人。已列目标的说明由 Agent 自己保持更新。列出的文件夹就是工作目录：编码 Agent 在里面建练习副本和输出文件夹，不用再问人。软件实例没有固定的 ID，所以真实运行只使用为这次运行启动的实例，由人或编码 Agent 启动，打开的文档也只来自清单里的文件和文件夹；编码 Agent 只关闭它自己启动的实例。工具自己的位置不算目标，也不列进清单：它的状态目录，以及属于这个状态目录的那份宿主组件（DSEC-050）。真实运行禁止触碰任何其他工程、实例或设备。真实运行使用的每份授权范围文件都必须只授予这些目标，以及为这次运行启动的实例里的新文档（DSEC-012），这样运行时会拒绝目标之外的任何写操作。

为什么：真实运行会做出真实的修改。在未经授权的工程或生产机器上，一次测试就可能造成真实的损失。对工作目录授权一次，Agent 就能在里面准备和运行全部测试，不用再问人，目录之外什么都碰不到。清单只有一份，就不会两份对不上。
检查：🤖 `check_project`：`docs/evidence/` 中每份记录的 `targets` 里的每一项都列在 Authorized Targets 里；`check_project` 和 `run_matrix` 拒绝覆盖整个磁盘或用户主目录的目标；`run_matrix` 按清单为每次运行写授权范围；👀 评审真实运行使用的其他授权范围文件。

### DVER-051 验收文档

每个工具都必须在 `docs/E2E.md` 和 `docs/E2E_zh.md` 中说明真实软件验收，按 DREPO-017 规定的章节和顺序来写。评审的人在这里能查到人授权了哪些目标（DVER-050）、行为矩阵怎样在真实软件上运行（DVER-031），以及运行留下了哪些记录（DVER-042）。

为什么：评审的人或下一任维护者，需要在一个地方看到可以跑什么、怎么跑、记录在哪里。
检查：🤖 `check_project` 检查两个文件是否齐全，章节是否完整、顺序是否正确。
