## 1 解释器：系统 python 没有 pcbnew

`pcbnew` 只随 KiCad 安装，不在 PyPI 上。系统 `python` 一定 `ImportError`。

```bash
kicad-cli context --compact    # 报告解析到的解释器与官方二进制
kicad-cli doctor  --compact    # 再说它们能不能用
```

Windows 上常见位置是 `<KiCad>/bin/python.exe`。找到后所有脚本都用它跑。

## 2 起止层：最容易误判成「布通率上不去」的静默失败

**这是全套里危害最大的一条。**

A\* 允许路径在顶层或底层起步时，如果起点那一层上并没有该网络的焊盘，
走出来的路径两端悬在空中：DRC 不报错（它只报悬空走线警告），ratsnest 也
不会减少。表现是走线段数涨了几百、未连接数纹丝不动。

正确做法：起止层只能取「该网络在该点已有铜的层」。

```python
def layers_at(R, x, y, ncode):
    i, j = R.gx(x), R.gy(y)
    out = [L for L in (F, B)
           if 0 <= i < R.W and 0 <= j < R.H and R.occ[L][j, i] == ncode]
    return out or [F, B]
```

修正这一条之后，某块板的未连接项从 96 直接掉到 35。

## 3 膨胀用圆形不用方形

可分离的方形膨胀快，但在对角线方向多封 √2 倍。0.65 mm 引脚间距下，
相邻焊盘边缘距中心线约 0.445 mm，而方形膨胀按半径 0.45 mm 算就正好把
合法的出脚通道封死，表现为引脚「怎么都出不来」。

用圆形结构元：`dx² + dy² ≤ r²`。见 `router.py` 的 `dilate()`。

## 4 放宽「本网络自身铜」的作用范围

为了让引脚从密集阵列出脚，需要允许路径踩在本网络自己的铜上
（`d &= ~(sub == nc)`）。两条限制缺一不可：

- **只在端点附近生效**（本实现取 1.6 mm）。全窗口放宽会让走线沿着自己
  已有的铜贴着异网焊盘走，产生 0.09 mm 级别的间距违规。
- **绝不能用于过孔校验**。过孔掩膜必须用未放宽的版本，否则过孔会被允许
  落在紧邻的异网焊盘上，DRC 报 `shorting_items` 和 `hole_clearance`。

## 5 SWIG 代理失效：活容器与 Remove 之后

`board.Zones()`、`board.GetFootprints()`、`board.GetTracks()` 返回的是活容器。

- **边遍历边增删会段错误**（退出码 139）。一律先 `list(...)` 快照。
- **`board.Remove()` 之后**，再调 `GetFootprints()` / `GetTracks()` 可能返回
  未解包的 `SwigPyObject`，访问成员抛 `AttributeError: 'SwigPyObject' object
  has no attribute 'Pads'`。**需要的焊盘列表要在任何 Remove 之前取完。**
- 同一进程内**反复 `LoadBoard`** 也会让代理退化。第二次拿到的 board 是裸
  `SwigPyObject`，`b.GetNetInfo()` 直接 `AttributeError`。多轮迭代请一轮一进程，
  由外层循环驱动（见第 17 条）。
- `b.Remove(t)` 后被移除对象仍需保持 Python 引用，否则可能提前回收。
- **反复增删之后连 `board.GetBoardEdgesBoundingBox()` 都会退化**，返回的对象
  没有 `GetLeft`。板框在布线期间不变，算一次缓存复用即可（`router.py` 的 `_EXTENT`）。

`kicad_lib.py` 的 `zones_of` / `tracks_of` / `footprints_of` / `all_pads` 已封好。

## 6 过孔单位陷阱：`GetDrillValue()` 返回纳米，且 `GetWidth()` 会卡死进程

两个坑叠在一起，危害极大：

**`GetWidth()` 不带层参数会卡死。** KiCad 10 里 `PCB_VIA::GetWidth()` 必须带层
参数。不带会触发 wxWidgets 断言，在无人值守环境下弹出对话框**永久阻塞**，
表现为脚本无输出、无退出；如果是多个进程并发跑，用户那边会看到弹框一个接一个。

**工具链必须对这类误用免疫，不能靠人记得。** `kicad_lib.import_pcbnew()` 里
已经先调了 `wx.DisableAsserts()`：

```python
try:
    import wx
    wx.DisableAsserts()
except Exception:
    pass
```

加上之后，故意误用 `GetWidth()` 会返回一个值（900000，纳米）而不是弹窗阻塞。
**所以取 pcbnew 一律走 `K.import_pcbnew()`，不要直接 `import pcbnew`** ——
直接 import 拿不到这层保险。让子代理写分析脚本时，这一条要写进提示里。

**`GetDrillValue()` 返回的是内部单位（纳米），不是毫米。** 当毫米用会让按它
计算涂布半径的代码算出上百万格的半径——numpy 切片会自动钳位到整个数组，
于是**一个过孔就把整层涂成它的网络**。占用栅格彻底报废，但不抛任何异常：
布线器照常运行、照常返回「布通 N 条」，只是一条都接不上。

实测该 bug 导致连续数轮布线原地踏步，且据此做出的「起点被困」诊断也是错的
（诊断脚本用了同一个函数）。修复后同一块板的诊断结论从「37/42 被困」
变成「35/42 可达」。

一律用 `kicad_lib.via_drill()`，它返回毫米并绕开断言。

**教训推广：任何 `Get*Value()` / `Get*()` 返回几何量的 pcbnew 接口，
用之前都要确认单位。** 内部单位是纳米，`ToMM` / `FromMM` 是唯一的换算入口。

## 7 `IsFilled()` 会骗人

`zone.IsFilled()` 返回真只说明「标记为已填充」，不代表真的有铜。真实判据是
填充多边形数：

```python
poly = zone.GetFilledPolysList(layer)
poly.OutlineCount()      # 0 表示这块铺铜是空的
```

多边形数为 0 时，平面上没有任何铜，所有靠它连通的焊盘都是断的。这会让
未连接数虚高一大截，误导后续所有判断。`board audit` 的「铺铜未真正填充」就查这个。

## 8 网络类：板内嵌的类名可能过期

`net.GetNetClassName()` 读的是板文件里内嵌的快照。改过 `.kicad_pro` 的
`netclass_patterns` 之后，板文件不会自动同步，于是脚本按旧类名取到错误线宽。

一律按 `.kicad_pro` 的 pattern 用 `fnmatch` 重新判定。`kicad_lib.NetClasses` 已封。

## 9 `GetUnconnectedCount` 需要参数

KiCad 9+ 签名是 `GetUnconnectedCount(aVisibleOnly)`。不传参抛 `TypeError`。

```python
board.BuildConnectivity()
n = board.GetConnectivity().GetUnconnectedCount(False)
```

## 10 numpy 标量不被 `FromMM` 接受

`pcbnew.FromMM()` 只收 `int` / `float` / `wxPoint` / `VECTOR2I`。传
`numpy.float64` 抛 `TypeError`。用 numpy 算坐标时记得 `float(x)`。

## 11 `.kicad_dru` 的 condition 必须单行

自定义规则的 `(condition "...")` 字符串跨行会让**整个规则文件解析失败且不报错**。
症状很有迷惑性：违规数不降反升（因为原本生效的规则也一起失效了）。

```lisp
# 对的
(rule "U201 封装内固有间隙"
	(constraint clearance (min 0.15mm))
	(condition "A.insideCourtyard('U201') && B.insideCourtyard('U201')"))
```

另外 KiCad 的 S-expression **不支持分号注释**，用 `#`。

## 12 设计规则存在 `.kicad_pro`，不在板文件里

`board.GetDesignSettings().m_MinThroughDrill` 之类可以写，但用 KiCad 打开工程时
会被 `.kicad_pro` 里的 `board.design_settings.rules` 覆盖。**独立加载板文件测出的
DRC 结果和在工程目录下跑出来的不一样**，容易误判修好了。

改规则一律改 `.kicad_pro`；验证 DRC 一律在工程目录下跑。

同理，把板文件复制到别处单独跑 DRC 会因为找不到 `fp-lib-table` 而把
全部封装报成 `lib_footprint_issues`——那是测试环境的假象，不是板的问题。


## 13 间距余量不能叠加：它会把合法的出脚车道判死

栅格布线器容易犯的一个错：为了补偿量化误差，在间距上统一加一个余量。
后果是把本来装得下的车道判成装不下。

实算（0.65 mm 引脚间距、0.40 mm 焊盘宽、0.20 mm 走线）：

```
邻脚焊盘边缘距本脚中心线 = 0.65 - 0.40/2 = 0.450 mm
真实所需                 = 0.10(半线宽) + 0.30(间距) = 0.400 mm   装得下
再加 0.10 mm 量化余量    = 0.500 mm                              装不下
```

对照实验能直接证伪：把板上走线全部清空、只留焊盘，看各引脚能否走出 5 mm。
本项目实测现行口径下仍有 4/59 根脚出不去，去掉余量后 0/59。**空板上都出不去，
说明不是布线顺序问题，任何排序或角度调整都救不回来。**

正确做法是把误差消灭在源头，而不是加全局余量：焊盘涂色原本用 `round` 对齐
栅格，最多少涂半格（0.05 mm），改为向外取整（左上 `floor`、右下 `ceil`）后
焊盘只会多占不会少占，余量就不必要了。见 `router.py` 的 `_paint_pad`。

## 14 SWIG 噪声会污染 stdout：信封固定取第一行

SWIG 在对象析构时会往 **C 层** stdout 打 `detected a memory leak of type ...`。
那些字节在执行期间就进了 C 缓冲，但往往晚于 Python 写的信封才刷出，于是
stdout 上出现「第一行是 JSON，后面跟着几百行噪声」。

试过的无效办法：`sys.stdout.flush()` 管不到 C 缓冲；`os._exit()` 在 Windows 上
仍会看到这些字节；`os.dup2` 重定向 fd 1 在 Windows 上行为不可靠（实测信封
反而跑到了 stderr）。

能减少但不能根除的办法：对象 `b.Add(x)` 之后设 `x.thisown = False`
（见 `kicad_lib.disown`），可消掉自己创建的对象那部分噪声。

**因此本 Skill 的约定是：stdout 的第一行是信封，后续行可能是 C 层诊断。**
解析时取第一行，不要整体 `json.load`。

## 15 提交宽度必须与校验掩膜一致，且放宽区不等于缩颈区

栅格布线器常同时维护几套膨胀掩膜：全宽正常间距 `blk_f`、缩颈 `blk_n`、
细间距封装内放宽间距 `blk_t`。两个独立的错误都出在「哪一格该用多宽」上。

**其一，提交宽度与校验掩膜脱节。** 路径在放宽区里按缩颈宽度校验通过，
提交时却按目标宽度落铜，DRC 立刻报间距违规。必须让每一格的提交宽度
等于校验它时用的宽度。

**其二（危害更大），把放宽区直接当缩颈区。** 放宽区表达的是**间距**
（庭院内部允许 0.15 mm），不是**线宽**。按「落在放宽区里就缩颈」提交，
一条 1.2 mm 的喇叭线只要路过某个细间距封装外扩 0.8 mm 的方框，
整段被压成 0.2 mm——实测 28 mm 里只有 2.2 mm 达标（8%）。
2 A 的线在 0.2 mm 上跑 26 mm，是会烧的。而且这类问题 DRC 不报、
未连接数不变，只能靠按网络统计实际落下的宽度才看得见。

正确判据是**只在必要处缩颈**：

```python
need_neck = [dilate(blk_f[L] & ~blk[L], 2) for L in (F, B)]
# blk_f 通不过、放宽后才通过的格子才缩颈；其余按目标宽度提交
```

这是安全的：更严的判据放行的格子，按全宽落铜必然合规。外扩 2 格是因为
宽度按线段给，一段跨两格，端点擦边时取保守值。

**判据必须用「未放宽」的全宽掩膜。** 端点附近为了出脚会放宽「本网络自身
铜」（第 4 条），于是自己焊盘那一格在放宽后的全宽掩膜里也是空的，恰恰在最
该缩颈的焊盘上判成不必缩颈：1.5 mm 的线直接铺在焊盘上压住邻脚，DRC 报
`shorting_items`。改用未放宽的掩膜后这类短路全部消失。

**放宽区的范围必须与 `.kicad_dru` 那条规则的作用域严格一致。** 规则条件写的是
`insideCourtyard`，放宽区就只能是庭院本身。曾经为了「覆盖出脚走廊」把它外扩
0.8 mm，等于在没有规则撑腰的那圈环里按 0.15 mm 布线，DRC 原样报回来：
「间距 0.3000 mm；实际 0.1500 mm」。栅格模型放宽什么，必须由设计规则说了算。

另外，缩颈半径宁小勿大。改成按格判定宽度之后，本以为放大缩颈区不再有代价，
实测相反：同一块板半径 1.0 mm 保住 6 条网络，2.5 mm 只剩 1 条，其余全被 DRC
自验回退——放宽的校验口径会让路径钻进事后填不回宽度的缝里。

## 16 DRC 自验回退必须迭代到闭合

栅格间距模型是近似的，最终裁判只能是 DRC。重布之后按网络粒度回退
「引入了 error 的网络」是对的，但**一轮不闭合**：

还原网络 A 之后，A 的**旧**路径可能与网络 B 的**新**粗线打架——这对冲突
在第一轮 DRC 里根本不存在，因为那时 A 还是新路径。实测一轮回退后
仍剩 2 条 clearance error，且两条都是「已还原的 VRAW」×「新的 DC_FUSED」。

所以要循环：跑 DRC → 回退肇事网络 → 重填重存 → 再跑 DRC，直到没有
error 或达到轮数上限。每轮只在**本次重布过且尚未回退**的网络里找肇事者，
不要去动用户原有的布线。

## 17 一个进程只能碰一块板一次

把第 5 条推到底：**同一进程里既不能跨 `Remove` 缓存代理，也不能反复
`LoadBoard`。** 两条路都试过，都会退化：

- 缓存权威列表 → `t.GetStart()` 返回不带 `.x` 的裸对象。
- 每次重新 `board.GetTracks()` → 到后期 `GetTracks()` 自己抛。
- 重新 `LoadBoard` → 第二次拿到的 board 连 `GetNetInfo` 都没有。

根因是进程内累积，不是某一处写法。逐网络重布这类天然需要多次加载的流程，
只能**一条网络一个子进程**：父进程只做调度与 DRC，子进程加载一次、改一条
网络、存盘、退出。跨进程要传的状态一律用几何快照（纯 JSON 的 dict），
不要传对象。`pcb_route.py --mode rewidth` 就是这么组织的，内部子命令是
`--internal --sub plan|one|revert|stats`。

顺带一条排错经验：**当 DRC 结果荒谬时，先怀疑自己的控制流，再怀疑几何模型。**
曾经重布之后对象数翻倍、连没动过的网络都报间距违规，花了几轮去查栅格与
掩膜，真正的原因是 `if mode == "rewidth":` 那一段执行完直接落进了
`else: mode_full(...)`，每次重布后又把整块板重新布了一遍。

## 18 量化余量只能加在全宽校验上

第 13 条说过不能在间距上统一加余量，那会把出脚车道判死。但完全不加也不对：
路径走的是格心连线，斜向一步的真实位置与被校验的格子最多差半个格对角线
（0.1 mm 栅格下 0.0707 mm），DRC 会报出「间距 0.3000 mm；实际 0.2842 mm」
这种差十几微米的欠量。

两者的解法是**分开**：余量只加在全宽校验的膨胀半径上，缩颈与放宽通道保持
不加。粗线本来就需要空地，多 0.08 mm 代价很小；细间距出脚那几格差 0.08 mm
就是通与不通的区别。见 `router.py` 的 `QUANT_DIAG`。

## 19 布不通先看拓扑，不要先怪走廊挤

有些「布线问题」根本不是布线问题。本项目在功放输出上耗了半个会话，
换顺序、整组拆光、调优先级、加宽走廊、准备改布局——全部无效，直到把
器件和引脚摊成一张表：

```
引脚从上到下：PR(66.8)  NR(68.7)  PL(71.3)  NL(72.6)
器件行从上到下：PL(69.2)  NL(77.4)  PR(85.7)  NR(93.9)
```

**完全颠倒。** 每条 R 通道的走线都必须斜穿过每条 L 通道的走线。四条 1.2 mm
的粗线互相交叉，在单层上是不可能实现的拓扑，跟走廊宽窄毫无关系。任何布线器、
任何参数都解不开——因为解不存在。

把两对通道的行位置对调（纯粹的坐标置换，不需要新面积、不改间距、
一个器件都不出板），交叉消失，DRC 立刻归零，喇叭线四条全部一次达标。

**判据：** 一条网络反复布不通时，先把「引脚的物理顺序」和「它要连的器件的
物理顺序」列出来比对。顺序不一致就是拓扑有交叉，先动布局，别动布线器。
`pcb_place.py` 就是干这个的。

## 20 缩颈半径必须覆盖整个扇出段

粗线从细间距封装出来时，要走完「车道从引脚间距展开到目标间距」这一段才能
展宽。0.65 mm 引脚间距、1.2 mm 目标线宽、0.3 mm 间距要求下，四条车道要展到
1.5 mm 间距，这段距离**远超 1 mm**。

缩颈半径取 1.0 时，线刚出焊盘就被要求展宽，必然失败，整条回落到缩颈宽度——
实测四条 OUT 全部只能拿到 0.20 mm，达标率 0%。取 4.0 时同样两条拿到 1.20 mm，
但多出 14 个 DRC error。本项目定在 2.5。

放大缩颈区**本身没有宽度代价**：缩颈是逐格判定的（`need_neck`），
`nz` 只是「允许更窄地校验」，实际宽度仍然逐格取全宽。代价来自放宽的校验
口径会让路径钻进事后填不回宽度的缝——所以也不能无限放大。

## 21 搬过器件之后，一切「还原旧几何」都是错的

整组拆重布带 DRC 自验回退（第 16 条）是对的，但前提是**器件没动过**。
一旦搬过位置，拆之前的走线连的是旧坐标上的焊盘，还原回去就是往板上塞一堆
通向空气的铜：未连接数不降，还跟新布的线打架。实测一轮管线因此卡在
9 个未连接，比不搬器件的 6 个还差。

搬动器件之后的正确做法（`--no-restore`）：布不通就**留空**交给后面的补布，
DRC 否掉的就**只删新线**，不还原任何旧几何。
